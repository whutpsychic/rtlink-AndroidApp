# 前言

​	每当遇到 Android 或 iOS 系统更新时，Flutter 的支持都不很及时；另外其可扩展性同样堪忧，我们能用什么原生的功能完全由三方决定，当官方不予支持时，则只能依靠野生的三方开发者所发布的开发包维持，而且偶尔会发生某个包在另一个平台不生效（报错）的情况，不得不安卓一套，iOS一套，不能实现实质上的一份代码打两份包。但这些都不算是严重问题，可怕的是当再次遇到系统更新大版本号时，很可能导致旧包不可用的情况发生。如果野生的三方包开发者没能及时更新，轻则导致部分功能不可用，严重则会导致整个 Flutter 框架轰然倒塌，而野生的开发者什么时候或者是否愿意继续更新该包则是一件完全不可控的事件。

​	Flutter 是谷歌公司负责开发维护的移动端框架，站在外国人的视角来看，他们不大可能会主动来兼容我国的“后起之秀”——鸿蒙系统。当鸿蒙崛起之时，Flutter 很有可能插不上手，即便是 Flutter 真的愿意兼容鸿蒙系统，但由当下已经存在的 Android 和 iOS 兼容情况来看，效果也不一定会好到哪里去。

​	综上，基于 Flutter 开发的移动端框架，其稳定性和可扩展性都有潜在的隐患，并且未来的前途也较为迷茫。因此我们应该尽量对应到各原生端开发模式当中去。




# 总览

​	目前我们的研发目标是，研发部一套初始化代码和说明文档，使得各交付部门可自行针对项目需求进行开发工作。因此我们采用的是 原生+h5 的 hybrid 混合开发模式。即由原生端负责搭建基本框架、打包和调取设备功能；h5 端负责业务逻辑实现，数据展示等。




# 移动端app技术最低要求

### 1. WebView 的嵌入

这里尤其要注意是否是一个完整可用的 webView，包括alert等基础函数的调用；另外需要注意 ```<input type="file" />``` 这个在Android端无响应巨大问题，以及仅拍照功能（capture=”camera”）。



###  2. 针对Webview的双向通信

####  2.1.Native 端向 web 端发送指令
也就是说 Native 端要可以向 web 发送数据或调用 web 端的方法；同时也意味着web端需要注册监听从native端传来的数据。



####  2.2.Web 端向 Native 端返回请求
从 Web 端往 Native 端传数据或调用 Native 端方法。
